# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

The current purpose of this project is to create an administrative tool for a local football club, in which the administrators can overview and manage membership fees.

The tool currently has two main purposes:

- **Swish QR codes.** Generate custom Swish QR codes for paying membership fees, prefilled with the club's Swish number, the amount and a message identifying the member and fee.
- **Fee status.** Let members check whether they have paid their fee for the current year.

Fees are marked as paid manually by an administrator after they have confirmed the payment. The application never verifies or receives payments itself; the QR codes are only a convenience for the payer.

## Rules to live by

- A QR code is never created in the frontend. It is always generated by the API and returned as an image.
- The amount of custom parameters when generating QR codes are limited to a list of names, and the type of membership. No amounts or custom messages (apart from the name list) influences the QR code generation in any way.
- The list of names **must** be properly validated and sanitized before being stored.
- The length of a message in a Swish payment must not exceed 50 characters.

## Architechture

The repository is a monorepo with two independent applications:

```
backend/    FastAPI application (Python)
frontend/   SvelteKit application (TypeScript)
```

The frontend talks to the backend only through the backend's HTTP JSON API. Neither side imports code from the other.

### Backend (FastAPI)

Organise the code by domain (e.g. `members`, `fees`, `payments`), not by technical layer. Each domain package contains:

```
backend/app/
  main.py              App factory: creates the FastAPI instance, registers routers and middleware
  core/
    config.py          Settings loaded from environment variables via a Pydantic `BaseSettings` class
    database.py        Async engine (`create_async_engine`), `async_sessionmaker` and the `get_db` dependency
  <domain>/
    router.py          `APIRouter` with the HTTP endpoints for the domain
    schemas.py         Pydantic models for request and response bodies
    models.py          SQLAlchemy ORM models
    service.py         Business logic and database queries
    dependencies.py    Domain-specific dependencies (e.g. fetch-or-404 helpers)
backend/alembic/       Alembic environment and migration scripts (`versions/`)
backend/alembic.ini
backend/tests/         Mirrors the structure of `app/`
```

- **Thin routers.** Endpoints validate input, call a service function and return a schema. Business logic and queries live in `service.py`, so they can be tested without HTTP.
- **Separate schemas from models.** Never return SQLAlchemy models directly. Define distinct Pydantic schemas for input and output (e.g. `MemberCreate`, `MemberUpdate`, `MemberRead`) and use `response_model` (or the return type annotation) on every endpoint. Configure read schemas with `model_config = ConfigDict(from_attributes=True)`.
- **Dependency injection.** Obtain the database session, settings and the current user through `Depends`, never through module-level globals. Use `Annotated` aliases (e.g. `DbSession = Annotated[AsyncSession, Depends(get_db)]`) to keep signatures short.
- **SQLAlchemy 2.0 style.** Declare models with `Mapped[...]` and `mapped_column()`, and query with `select()` rather than the legacy `session.query()` API.
- **Async all the way.** Endpoints and service functions are `async def` and use an `AsyncSession` (`await session.execute(...)`, `await session.commit()`). Create the session factory with `expire_on_commit=False`.
  - Lazy loading does not work with async sessions. Load relationships explicitly with `selectinload()` / `joinedload()`, and declare relationships with `lazy='raise'` so accidental lazy loads fail loudly instead of silently.
  - Never call blocking I/O inside an `async def`. If blocking or CPU-heavy work is unavoidable (e.g. a slow third-party library), run it with `run_in_threadpool`.
- **Migrations.** All schema changes go through Alembic (initialised with the async template, `alembic init -t async`). Generate migrations with `alembic revision --autogenerate`, review them by hand before committing, and never use `Base.metadata.create_all()` in application code. The Alembic `env.py` takes the database URL from the settings class and `target_metadata` from the shared declarative `Base`, with all models imported.
- **Configuration.** All secrets and environment-specific values (database URL, CORS origins, etc.) come from environment variables via the settings class. Nothing environment-specific is hard-coded.
- **Errors.** Raise `HTTPException` (or domain exceptions mapped to HTTP responses via exception handlers) with explicit status codes. Services raise domain exceptions; routers or handlers translate them to HTTP.
- **Money.** Store monetary amounts as integers in the smallest currency unit (öre) or as `Numeric`, never as `float`.
- **QR codes.** QR code generation lives in its own service module and is exposed through an endpoint returning an image response (e.g. `image/png`), so the frontend can use it directly as an `<img>` source.
- **API versioning.** Mount all routers under a common prefix (e.g. `/api/v1`) and tag them per domain so the generated OpenAPI docs stay organised.
- **Tests.** Use pytest with `httpx.AsyncClient` (via `ASGITransport`) and async tests marked with `@pytest.mark.anyio` (the AnyIO pytest plugin ships with FastAPI's dependencies). Override `get_db` via `app.dependency_overrides` to run tests against a dedicated PostgreSQL test database, with the schema created by running the Alembic migrations and each test isolated in a rolled-back transaction. Test services directly for business rules and endpoints for HTTP behaviour.

### Frontend (SvelteKit)

```
frontend/src/
  lib/
    api/               Typed API client: one module per backend domain, plus shared fetch wrapper
    components/
      ui/              shadcn-svelte generated components
      <feature>/       App-specific components grouped by feature (e.g. members, fees)
    stores/            Shared state (`.svelte.ts` modules using runes)
    types/             TypeScript types mirroring the backend's response schemas
    utils/             Pure helper functions (formatting of dates, currency, etc.)
  routes/
    +layout.svelte     App shell (navigation, page frame)
    +layout.ts         `export const ssr = false;` (SPA mode)
    +error.svelte      Error page
    members/
      +page.svelte     Member list
      +page.ts         `load` function fetching the list via `lib/api`
      [id]/
        +page.svelte
        +page.ts
```

- **SPA mode.** FastAPI owns all data, business logic and authentication, so SvelteKit runs as a client-side app: `adapter-static` with a `fallback` page and `ssr = false` in the root layout. Do not add SvelteKit server code (`+page.server.ts`, `+server.ts`, `hooks.server.ts`); there is exactly one backend.
- **API access.** In development, the Vite dev server proxies `/api` to the FastAPI backend, so the frontend always calls relative `/api/v1/...` URLs and no CORS setup is needed. In production, nginx in the frontend container serves both under the same origin (see Docker below). The proxy target is read from an environment variable so it works both locally (`http://localhost:8000`) and inside Docker (`http://backend:8000`).
- **Data loading in `load` functions.** Pages get their data from `load` in `+page.ts` / `+layout.ts`, passing SvelteKit's provided `fetch` into the `lib/api` functions. Pages receive it with `let { data }: PageProps = $props();`, using the generated types from `./$types`. Use `error(404, ...)` from `@sveltejs/kit` for missing resources so `+error.svelte` handles it.
- **Mutations.** Create/update/delete calls happen from event handlers via `lib/api`, followed by `invalidate()` / `invalidateAll()` to re-run the affected `load` functions, rather than patching local copies of the data by hand. Navigate programmatically with `goto` from `$app/navigation`.
- **Svelte 5 runes.** Use `$state`, `$derived`, `$effect` and `$props` rather than the legacy `let`-reactivity, `$:` statements and `export let`. Prefer `$derived` over `$effect` for computed values; reserve `$effect` for genuine side effects.
- **Typed props.** Type component props with an interface: `let { member }: { member: Member } = $props();`.
- **All HTTP calls go through `lib/api`.** Components never call `fetch` directly. The shared wrapper handles the base URL, JSON parsing and error handling, and returns typed results.
- **Keep types in sync with the backend.** Frontend types in `lib/types` mirror the backend's Pydantic response schemas. Prefer generating them from the backend's OpenAPI schema over writing them by hand.
- **shadcn-svelte components.** Add components with the shadcn-svelte CLI into `lib/components/ui`. Build app-specific components by composing them rather than heavily modifying the generated files, so they can be updated later.
- **Small, focused components.** Pages (fed by their `load` functions) handle layout; feature components handle presentation and emit events via callback props (e.g. `onsave`). Shared state that spans pages lives in `lib/stores`, not in deeply passed props.
- **Formatting.** Format currency and dates in one place (`lib/utils`) using `Intl` with the Swedish locale, so presentation is consistent across the app.

### Docker

```
docker-compose.yml            Base stack: db, backend, frontend
docker-compose.override.yml   Development overrides (hot reload, exposed ports), applied automatically by `docker compose up`, making development the default
.env.example                  Template for `.env` (committed); `.env` holds real values and is git-ignored
backend/Dockerfile
backend/entrypoint.sh         Runs migrations, then starts the given command
backend/.dockerignore
frontend/Dockerfile
frontend/nginx.conf
frontend/.dockerignore
```

Services in `docker-compose.yml`:

| Service    | Image / build                                    | Purpose                                                                                                                                  |
| ---------- | ------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `db`       | `postgres:<major>-alpine` (pinned major version) | PostgreSQL with data in a named volume. Has a `pg_isready` healthcheck.                                                                  |
| `backend`  | `backend/Dockerfile`                             | Runs the Alembic migrations on startup, then serves FastAPI on `0.0.0.0:8000`. Depends on `db` with `condition: service_healthy`.        |
| `frontend` | `frontend/Dockerfile`                            | nginx serving the built SvelteKit app and proxying `/api` to `backend:8000`. The only service exposing a port to the host in production. |

- **Configuration via environment.** All configuration (database credentials, `DATABASE_URL`, CORS origins, etc.) comes from `.env` through `env_file` / `environment` in compose, matching the backend settings class. Inside the compose network, services address each other by service name (e.g. `postgresql+asyncpg://...@db:5432/...`), never `localhost`. Secrets are never baked into images.
- **Migrations run as part of the backend container.** `backend/entrypoint.sh` is the image's `ENTRYPOINT`: it runs `alembic upgrade head` and then `exec "$@"`, handing over to the container's `CMD`. The script uses `set -e`, so a failed migration stops the container before the API starts. Because migrations live in the entrypoint, overriding the command (e.g. with `--reload` in development) still runs them.
- **Backend Dockerfile.** Based on `python:3.13-slim`. Copy the dependency manifest and install dependencies before copying the source, so the dependency layer is cached. Run as a non-root user. The default `CMD` is `uvicorn app.main:app --host 0.0.0.0 --port 8000 --proxy-headers` (proxy headers, since it sits behind nginx).
- **Frontend Dockerfile.** Multi-stage: a `node` stage installs dependencies with the lockfile (`npm ci`) and runs `npm run build`; a final `nginx:alpine` stage contains only the static build output and `nginx.conf`. The nginx config uses `try_files $uri /index.html` as the SPA fallback and `location /api/ { proxy_pass http://backend:8000; }` for the API.
- **Development override.** `docker-compose.override.yml` bind-mounts the source directories, runs the backend with `uvicorn --reload` and the frontend with the Vite dev server (`--host 0.0.0.0`), and exposes the ports for the backend, the frontend dev server and the database to the host. Nothing development-only belongs in the base `docker-compose.yml`. `docker compose up` gives the development setup; for a production-like run, skip the override with `docker compose -f docker-compose.yml up`.
- **`.dockerignore`.** Each project excludes `.git`, `.env`, caches and local dependency/build folders (`.venv`, `__pycache__`, `node_modules`, `.svelte-kit`, `build`) to keep build contexts small and avoid leaking local files into images.
- **Tests in Docker.** Backend tests run with `docker compose run --rm --entrypoint pytest backend`, against a separate test database (never the development database). The entrypoint is bypassed because the test setup applies migrations to the test database itself.
