# bpif-admin

An administrative tool for BPIF.

## Quick start (development)

Requires Docker with Compose.

```sh
cp .env.example .env
docker compose up --build
```

`docker compose up` applies `docker-compose.override.yml` automatically, which gives the development setup with hot
reload for both the backend and the frontend.

| URL                                    | What                                       |
| -------------------------------------- | ------------------------------------------ |
| http://localhost:5173                  | Frontend (Vite dev server, proxies `/api`) |
| http://localhost:8000/api/docs         | Backend OpenAPI docs                       |
| http://localhost:8000/api/v1/health    | Backend health check                       |
| `localhost:5432`                       | PostgreSQL (credentials from `.env`)       |

After changing `frontend/package.json`, run `docker compose up --build -V` so the `node_modules` volume is recreated.

> **Updating an existing checkout:** `.env` must contain every variable in `.env.example`, or `docker compose up` stops
> with a missing-variable error. `TEST_DATABASE_URL` and `SWISH_NUMBER` are the most recent additions.

## Tests (backend)

```sh
docker compose run --rm --entrypoint pytest backend
docker compose run --rm --entrypoint pytest backend tests/health   # one folder
docker compose run --rm --entrypoint pytest backend -k migrations  # by name
```

- The tests run against the `bpif_test` database (`TEST_DATABASE_URL`), which is dropped and recreated on every run.
  The development database is never touched: the harness refuses to run if `TEST_DATABASE_URL` equals `DATABASE_URL`
  or if the database name doesn't end in `_test`.
- The entrypoint is bypassed because the harness applies the Alembic migrations to the test database itself.
- Each test runs in a transaction that is rolled back afterwards, so tests don't see each other's data.
- Pure unit tests (e.g. `tests/payments`) need no database and also run on the host: `cd backend && uv run pytest
  tests/payments`.
- Formatting: `docker compose run --rm --entrypoint autopep8 backend --diff --exit-code -r app tests alembic scripts`
  (drop `--diff --exit-code` and add `--in-place` to fix).

## Frontend scripts

Run in `frontend/` (or in the container with `docker compose exec frontend npm run <script>`):

| Script                   | What                                                                         |
| ------------------------ | ---------------------------------------------------------------------------- |
| `npm run lint`           | ESLint                                                                       |
| `npm run check`          | svelte-check (type checking)                                                 |
| `npm run build`          | Production build into `build/`                                               |
| `npm run generate:types` | Regenerates `src/lib/types/api.ts` from the running backend's OpenAPI schema |

`generate:types` reads the schema through the Vite dev server's `/api` proxy, so `docker compose up` must be running.
Run it whenever a backend request or response schema changes, and commit the result in the same commit as the backend
change. CI fails if the committed types don't match the backend.

Generated code is never edited by hand:

- `src/lib/types/api.ts` is generated by `openapi-typescript`. Add friendly aliases in `src/lib/types/<domain>.ts`
  instead, e.g. `export type Health = components['schemas']['HealthRead'];`.
- `src/lib/components/ui/` and `src/lib/utils/cn.ts` are generated by the shadcn-svelte CLI. Add components with
  `npx shadcn-svelte@latest add <component>` and build app-specific components in `src/lib/components/<feature>/`.

## Production

```sh
docker compose -f docker-compose.yml -f docker-compose.production.yml up -d --build
```

Only nginx is published, on `FRONTEND_PORT` (default 8080). It serves the frontend and proxies `/api` to the backend.

## Test deployment (GitHub Pages)

For testing only: the frontend is published to GitHub Pages and talks to a backend on a local machine through a
temporary Cloudflare tunnel.

> **Warning:** the management endpoints have no login until step 4, and the tunnel URL is public. Anyone who finds it
> can read and change the data, so only use fake data and only keep the tunnel running while testing.

The `Deploy to GitHub Pages` workflow deploys `master` each time CI passes on it.

**One-time setup**

1. Under **Settings > Pages**, set **Source** to **GitHub Actions**.
2. Add `CORS_ORIGINS=["https://karlnilsson.github.io"]` to `.env`. The value is the origin only, with no repository
   path.

**Starting a test session**

1. Start the backend with `docker compose up -d`.
2. Run `cloudflared tunnel --url http://localhost:8000` and copy the `https://<random>.trycloudflare.com` URL.
3. Under **Settings > Secrets and variables > Actions**, set the repository secret `API_ORIGIN` to that URL, with no
   trailing slash.
4. Under **Actions > Deploy to GitHub Pages**, choose **Run workflow** on `master`.

The app is then at https://karlnilsson.github.io/bpif-admin/. The tunnel gets a new URL every time it restarts, and the
URL is built into the frontend, so repeat steps 2-4 after each restart.

`API_ORIGIN` is stored as a secret to keep it out of the repository and the workflow logs, but it isn't hidden from
visitors: it ends up in the published JavaScript. Never put anything in a `VITE_` variable that must stay private.
